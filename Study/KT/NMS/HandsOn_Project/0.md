# 프로젝트 기획 정리

## 1. 프로젝트 방향

**프로젝트 1: 통합 모니터링·로깅 시스템 구축**

선정이유: 다른 프로젝트는 이전 기본/심화에서 다뤘던 부분들이랑 겹쳐 모니터링 파트를 고도화해보기 위해 프로젝트 1번을 선택. 1번을 수행하며 다른 프로젝트에 명시되어 있는 과업들을 추가적으로 해보려고 한다. 
<br>
일반 이커머스 서비스에 특정 시간에만 판매하는 한정상품을 추가합니다.
한정판매가 시작되면 다수의 사용자가 동시에 접속하도록 부하를 발생시키고, 이 과정에서 발생하는 트래픽 증가, 응답 지연, 오류, 장애와 복구 과정을 관찰하는 것을 목표로 한다.
<br>

### 프로젝트 주제

> 가상 대기열 기반 한정판매 이커머스 서비스의 트래픽 급증 및 장애 분석

이커머스 기능 자체를 크게 만드는 것이 목적이 아니라, 실제 서비스와 유사한 트래픽 상황을 만들고 이를 메트릭·로그·트레이싱으로 분석하는 것을 이번 프로젝트의 메인으로 잡았다.
<br>

## 2. 서비스 운영 방식

평상시에는 일반적인 상품 구매가 가능하도록 설계한다.

```text
회원가입 및 로그인
→ 상품 목록 조회
→ 상품 상세 조회
→ 장바구니 추가
→ 주문
→ 결제
→ 주문 완료
```

특정 시간에는 한정판매 이벤트를 진행합니다.

```text
한정상품 판매 예정 표시
→ 판매 시작 시간 카운트다운
→ 판매 시작과 동시에 사용자 접속 증가
→ 사용자 대기열 등록
→ 대기 순번 안내
→ 순서가 된 사용자만 구매 화면 입장
→ 재고 확인 및 차감
→ 주문 생성
→ 결제
→ 구매 성공 또는 품절
```
<br>

## 3. 서비스
<br>

### 1. 회원 서비스

사용자를 식별하고 구매 이력을 사용자별로 연결하기 위해 사용합니다.

#### 포함 기능

* 회원가입
* 로그인
* 로그아웃
* 사용자 정보 조회
* 로그인 사용자 인증
* 사용자별 한정상품 중복 구매 제한
<br>

#### 필요한 이유

* 실제 사용자 흐름을 구성할 수 있음
* 특정 사용자 요청을 로그와 추적 정보에서 확인할 수 있음
* 한 명이 한정상품을 여러 번 구매하는 것을 방지할 수 있음
<br>

### 2. 상품 서비스

일반 상품과 한정판매 상품을 관리한다.

#### 포함 기능

* 상품 목록 조회
* 상품 상세 조회
* 일반 상품과 한정상품 구분
* 상품 가격 및 재고 표시
* 한정판매 시작·종료 시간 설정
* 판매 전·판매 중·판매 종료 상태 표시
<br>

#### 필요한 이유

* 평상시 트래픽과 한정판매 트래픽을 비교할 수 있음
* 상품 조회 요청 증가와 응답 지연을 관찰할 수 있음
* 한정판매라는 명확한 트래픽 집중 시나리오를 만들 수 있음
<br>

### 3. 장바구니 서비스

일반 상품을 구매하기 전에 보관하는 기능.
<br>

#### 포함 기능

* 장바구니 상품 추가
* 장바구니 조회
* 상품 수량 변경
* 상품 삭제
* 장바구니 상품 주문
<br>

#### 적용 범위

장바구니는 일반 상품에만 적용합니다.

한정상품은 장바구니에 담지 않고, 대기열 통과 후 바로 구매하도록 구성합니다. (**^추후 개선^**)
<br>
#### 필요한 이유

한정상품을 장바구니에 장시간 보관하게 하면 재고 선점과 만료 처리가 복잡해지기 때문입니다.

---

### 4. 대기열 서비스

한정판매 시작 시 사용자가 한꺼번에 구매 API로 들어오는 것을 막고 순차적으로 입장시키는 핵심 기능입니다.

#### 포함 기능

* 대기열 등록
* 중복 등록 방지
* 현재 대기 순번 조회
* 앞에 남은 사용자 수 표시
* 일정 인원씩 구매 화면 입장
* 구매 가능 사용자에게 입장 권한 발급
* 일정 시간이 지나면 입장 권한 만료

#### 필요한 이유

* 한정판매 시 트래픽을 제어할 수 있음
* 현재 대기자 수와 평균 대기시간을 관찰할 수 있음
* 대기열이 길어질 때 응답 지연과 시스템 부하 변화를 확인할 수 있음
* 대기열 장애 시 전체 구매 흐름에 미치는 영향을 분석할 수 있음

---

### 5. 주문 서비스

사용자의 구매 요청을 실제 주문 데이터로 생성합니다.

#### 포함 기능

* 일반 상품 주문
* 한정상품 주문
* 주문 내역 조회
* 주문 상태 관리
* 사용자당 한정상품 1개 구매 제한
* 재고 부족 시 품절 처리

#### 주문 상태 예시

```text
주문 생성
→ 결제 대기
→ 결제 완료
→ 결제 실패
→ 주문 취소
```

#### 필요한 이유

주문 생성부터 결제 완료까지 하나의 사용자 요청 흐름을 추적할 수 있습니다.

---

### 6. 결제 서비스

실제 카드 결제가 아닌 테스트용 결제를 구현합니다.

#### 포함 기능

* 정상 결제 성공
* 결제 실패
* 결제 응답 지연
* 결제 처리 시간 초과
* 결제 실패 시 주문 상태 변경
* 한정상품 결제 실패 시 재고 복구

#### 필요한 이유

결제 서비스에서 의도적으로 지연과 오류를 발생시켜 다음을 검증할 수 있습니다.

* 결제 오류율 증가
* 전체 구매 응답시간 증가
* 장애 알림 발생
* 실패 요청 로그 확인
* 어느 구간에서 지연됐는지 추적
* 결제 실패 후 재고가 정상적으로 복구되는지 확인

* 마우스

* 한정판 키보드 100개
* 한정판 헤드셋 50개

한정상품은 사용자당 1개만 구매할 수 있도록 제한합니다.

## 7. 프로젝트 과업과 연결

### 과업 1. 환경 구축 및 대상 서비스 배포

회원, 상품·주문, 대기열, 결제 서비스를 배포합니다.

#### 필요한 이유

서로 다른 서비스가 연결된 환경을 만들어야 한 요청이 여러 서비스를 거치는 과정을 관찰할 수 있습니다.

---

### 과업 2. Observability 아키텍처 설계

다음 흐름을 기준으로 전체 구조를 설계합니다.

```text
사용자 요청
→ 서비스 처리
→ 메트릭·로그·추적 정보 수집
→ 대시보드 확인
→ 장애 알림
→ 원인 분석
→ 복구
```

#### 필요한 이유

단순히 서버 상태만 보는 것이 아니라, 장애 발견부터 원인 분석과 복구까지 연결하기 위해 필요합니다.

---

### 과업 3. 메트릭 대시보드 구축

다음 대시보드를 구성합니다.

1. 전체 서비스 상태
2. 대기열 현황
3. 상품·재고·주문
4. 결제
5. 서버 및 데이터 저장소 상태

#### 필요한 이유

정상 상황과 한정판매 상황의 차이를 수치로 비교할 수 있습니다.

---

### 과업 4. 구조화 로그 수집

각 로그에 다음 정보를 포함합니다.

* 사용자
* 상품
* 주문번호
* 요청 추적 번호
* 서비스명
* 오류 코드
* 처리 결과

#### 필요한 이유

결제 실패나 주문 오류가 발생했을 때 특정 사용자와 주문의 전체 처리 과정을 검색할 수 있습니다.

---

### 과업 5. 분산 추적

한정상품 구매 요청이 각 서비스를 통과하는 흐름을 추적합니다.

```text
사용자 인증
→ 입장 권한 확인
→ 재고 차감
→ 주문 생성
→ 결제 처리
→ 주문 상태 변경
```

#### 필요한 이유

전체 요청 중 어느 서비스에서 시간이 오래 걸렸는지, 어느 구간에서 실패했는지 확인할 수 있습니다.

---

### 과업 6. 알림 규칙 작성

다음 상황에 대해 알림을 발생시킵니다.

* 서버 오류율 증가
* 주문 응답시간 증가
* 결제 성공률 감소
* 대기열 길이 급증
* 평균 대기시간 증가
* 데이터베이스 연결 부족
* 서비스 재시작

#### 필요한 이유

운영자가 대시보드를 계속 보고 있지 않아도 장애를 빠르게 인지할 수 있습니다.

---

### 과업 7. SLO와 Error Budget 측정

다음 목표를 정의합니다.

* 구매 서비스 가용성
* 주문 요청 응답시간
* 결제 성공률
* 대기열 처리 성공률

#### 필요한 이유

서비스가 단순히 동작하는지를 넘어, 정해진 품질 수준을 만족하는지 측정하기 위해 필요합니다.

---

### 과업 8. 부하 및 장애 시뮬레이션

#### 부하 시나리오

한정판매 시작과 동시에 다수의 사용자가 접속하고 구매를 시도합니다.

#### 장애 시나리오

* 결제 서비스 실패
* 결제 처리 지연
* 대기열 처리 지연
* 주문 서비스 종료
* 데이터베이스 연결 부족

#### 필요한 이유

실제 장애 상황에서 메트릭·로그·추적·알림이 제대로 동작하는지 검증하기 위해 필요합니다.

---

### 과업 9. Runbook 작성

알림별 대응 절차를 작성합니다.

예시:

```text
결제 오류율 증가 알림
→ 결제 서비스 상태 확인
→ 최근 오류 로그 조회
→ 실패 요청 추적
→ 원인 확인
→ 서비스 복구
→ 결제 실패 주문 및 재고 상태 확인
```

#### 필요한 이유

장애 발생 시 담당자가 정해진 절차에 따라 빠르게 대응할 수 있습니다.

## 9. 최종 프로젝트 설명

> 일반 상품을 조회하고 장바구니를 통해 구매할 수 있는 웹 기반 이커머스 서비스를 제작한다. 특정 시간에는 한정 수량 상품을 판매하고, 판매 시작과 동시에 다수의 사용자가 접속하도록 부하를 발생시킨다. 사용자는 가상 대기열을 통해 순차적으로 구매 화면에 입장하며, 재고 차감·주문·결제 과정을 거친다. 프로젝트에서는 이 과정에서 발생하는 트래픽 증가, 응답 지연, 오류, 시스템 과부하와 장애 복구 상황을 메트릭·로그·분산 추적으로 분석한다. 또한 알림 규칙, SLO, Error Budget과 장애별 Runbook을 작성하여 실제 운영과 유사한 장애 대응 흐름을 검증한다.
