# 프로젝트 기획 정리

## 1. 프로젝트 방향

**프로젝트 1: 통합 모니터링·로깅 시스템 구축**

**선정 이유:**  
이전 기본·심화 프로젝트에서 애플리케이션 배포, Kubernetes 환경 구성, 서비스 메시 및 기본 모니터링을 경험하였다. 이번 프로젝트에서는 기존 내용을 반복하기보다 메트릭·로그·분산 추적을 통합하여 Observability 환경을 고도화하기 위해 프로젝트 1번을 선택하였다.

호텔 예약 서비스에 특정 시간에만 진행되는 한정 특가 이벤트를 추가한다.

특가 예약이 시작되면 다수의 사용자가 동시에 호텔을 조회하고 예약하도록 부하를 발생시키며, 이 과정에서 발생하는 트래픽 증가, 응답 지연, 예약 실패, 객실 재고 경쟁, 장애 및 복구 과정을 관찰하는 것을 목표로 한다.

### 프로젝트 주제

> 호텔 한정 특가 예약 서비스의 트래픽 급증 및 장애 분석

호텔 예약 기능 자체를 크게 만드는 것이 목적이 아니라, 실제 서비스와 유사한 특가 예약 트래픽과 장애 상황을 구성하고 이를 메트릭·로그·분산 추적으로 분석하는 것을 프로젝트의 중심으로 한다.

---

## 2. 서비스 운영 방식

평상시에는 사용자가 지역과 날짜를 기준으로 호텔을 검색하고 객실 정보를 조회할 수 있도록 설계한다.

```text
회원가입 및 로그인
→ 지역 및 숙박 날짜 입력
→ 호텔 검색
→ 호텔 목록 조회
→ 호텔 상세 조회
→ 객실 및 가격 확인
→ 예약 가능 여부 확인
→ 예약
→ 예약 완료
```

특정 시간에는 한정 수량의 호텔 특가 이벤트를 진행한다.

```text
특가 호텔 예약 예정 표시
→ 예약 시작 시간 카운트다운
→ 예약 시작과 동시에 사용자 접속 증가
→ 특가 호텔 및 객실 조회
→ 객실 재고 확인
→ 예약 요청
→ 객실 재고 차감
→ 예약 생성
→ 예약 성공 또는 매진
```

추후 트래픽 제어 기능을 고도화하는 경우 가상 대기열을 적용한다.

```text
특가 예약 시작
→ 사용자 대기열 등록
→ 대기 순번 확인
→ 순서가 된 사용자만 예약 화면 입장
→ 객실 재고 확인
→ 예약 진행
```

## 3. 서비스 구성

### 1. 회원 서비스

사용자를 식별하고 사용자별 예약 정보와 요청 흐름을 연결하기 위해 사용한다.

#### 주요 기능

- 회원가입
- 로그인
- 사용자 정보 조회
- 사용자 인증
- 사용자별 예약 내역 관리
- 동일 특가 상품 중복 예약 제한

#### 필요한 이유

- 실제 사용자 기반의 예약 흐름을 구성할 수 있음
- 특정 사용자 요청을 로그와 Trace에서 확인할 수 있음
- 한 명의 사용자가 동일한 특가 객실을 여러 번 예약하는 것을 방지할 수 있음

---

### 2. 호텔 검색 서비스

사용자가 지역과 날짜 등의 조건을 기준으로 호텔을 검색하고 상세 정보를 조회하는 서비스다.

#### 주요 기능

- 호텔 목록 조회
- 지역별 호텔 검색
- 호텔 상세 조회
- 객실 및 가격 조회
- 일반 객실과 특가 객실 구분
- 예약 가능 여부 표시

#### 필요한 이유

- 평상시 트래픽과 특가 이벤트 트래픽을 비교할 수 있음
- 검색 요청 증가에 따른 응답 지연을 관찰할 수 있음
- 호텔 예약 서비스에서 가장 많이 발생하는 조회 트래픽을 재현할 수 있음

---

### 3. 특가 이벤트 서비스

특정 시간에 진행되는 호텔 한정 특가 이벤트를 관리한다.

#### 주요 기능

- 특가 이벤트 목록 조회
- 특가 호텔 상세 조회
- 이벤트 시작 및 종료 시간 설정
- 예약 예정·예약 가능·매진·종료 상태 표시
- 특가 가격 및 객실 수량 관리
- 이벤트별 예약 요청 관리

#### 필요한 이유

- 특정 시간에 트래픽이 집중되는 상황을 만들 수 있음
- 이벤트 시작 전후의 요청량과 응답시간을 비교할 수 있음
- 한정된 객실에 다수의 사용자가 동시에 접근하는 상황을 검증할 수 있음

---

### 4. 예약 및 객실 재고 기능

사용자의 예약 요청을 처리하고 호텔별 객실 수량을 관리한다.

#### 주요 기능

- 예약 가능 여부 확인
- 객실 재고 확인 및 차감
- 예약 생성
- 예약 내역 조회
- 객실 부족 시 매진 처리
- 예약 실패 또는 취소 시 재고 복구
- 초과 예약 방지

#### 필요한 이유

- 여러 사용자가 동일한 객실을 동시에 예약하는 상황을 만들 수 있음
- 객실 재고와 예약 데이터의 정합성을 검증할 수 있음
- 검색부터 예약 완료까지 전체 요청 흐름을 추적할 수 있음

---

### 5. 결제 서비스

실제 카드 결제가 아닌 테스트용 결제 기능을 구현한다.

#### 주요 기능

- 정상 결제
- 결제 실패
- 결제 응답 지연
- 결제 시간 초과
- 결제 실패 시 예약 상태 변경
- 결제 실패 시 객실 재고 복구

#### 필요한 이유

결제 서비스에서 의도적으로 지연과 오류를 발생시켜 다음 내용을 검증할 수 있다.

- 결제 오류율 증가
- 전체 예약 응답시간 증가
- 장애 알림 발생
- 실패 요청 로그 확인
- 분산 추적을 통한 지연 구간 확인
- 결제 실패 후 객실 재고 복구 여부 확인

> 결제 서비스는 기본 Observability 환경 구축 이후 추가하는 확장 기능으로 구성한다.

---

### 6. 가상 대기열 서비스

특가 예약 시작 시 사용자가 한꺼번에 예약 API로 들어오는 것을 방지하고 일정 인원씩 입장시키는 기능이다.

#### 주요 기능

- 대기열 등록
- 중복 등록 방지
- 현재 대기 순번 조회
- 예상 대기시간 표시
- 일정 인원씩 예약 화면 입장
- 입장 권한 발급 및 만료

#### 필요한 이유

- 특가 예약 시 발생하는 트래픽을 제어할 수 있음
- 대기자 수와 평균 대기시간을 관찰할 수 있음
- 대기열 장애가 전체 예약 흐름에 미치는 영향을 분석할 수 있음

> 가상 대기열은 기본 특가 예약 기능 완료 후 추가하는 개선 기능으로 구성한다.

## 4. 호텔 상품 구성

호텔 데이터는 서비스 흐름과 부하 테스트를 확인할 수 있는 최소한의 범위로 구성한다.

### 일반 호텔

일반적인 호텔 검색과 조회 흐름을 보여주기 위한 상품이다.

- 서울 시티 호텔
- 부산 오션 호텔
- 제주 스테이 호텔
- 강릉 비치 리조트
- 경주 한옥 스테이

### 한정 특가 호텔

트래픽 급증과 객실 재고 경쟁을 만들기 위한 상품이다.

- 제주 스테이 여름 특가 10실
- 부산 오션뷰 주말 특가 10실
- 서울 호캉스 특가 10실

한정 특가 객실은 사용자당 동일 상품을 한 번만 예약할 수 있도록 제한한다.

## 7. Observability 구성

프로젝트에서는 메트릭·로그·분산 추적을 통합하여 동일한 요청의 전체 흐름을 확인할 수 있도록 구성한다.

```text
애플리케이션 및 Kubernetes 메트릭
→ Prometheus
→ Grafana

애플리케이션 로그
→ Loki
→ Grafana

서비스 간 요청 추적
→ OpenTelemetry
→ Tempo
→ Grafana
```

Grafana에서 오류율이나 응답 지연을 확인한 후, 해당 시간대의 로그와 Trace를 연결하여 문제가 발생한 서비스와 지연 구간을 분석한다.

## 8. 부하 및 장애 검증

### 부하 테스트

- 평상시 호텔 검색 트래픽
- 특가 이벤트 시작 직후 트래픽 급증
- 한정 객실 수량보다 많은 동시 예약 요청
- 사용자 수가 단계적으로 증가하는 상황
- 결제 서비스 지연 및 실패

### 장애 테스트

- 서비스 Pod 강제 종료
- CPU 및 메모리 부하
- 데이터베이스 연결 부족
- 서비스 간 통신 실패
- 예약 또는 결제 서비스 응답 지연
- 일정 비율의 오류 응답 발생

장애 발생 시 Grafana 대시보드, Loki 로그, Tempo Trace 및 Kiali 서비스 그래프를 통해 장애 원인과 영향 범위를 분석한다.

## 9. 운영 검증 항목

### 알림

- 5xx 오류율 증가
- p95 응답시간 증가
- CPU 및 메모리 사용률 증가
- Pod 재시작
- 데이터베이스 연결 부족
- 예약 실패율 증가
- 결제 실패율 증가

### SLI·SLO

- 서비스 가용성
- 호텔 검색 응답시간
- 특가 조회 응답시간
- 예약 성공률
- 시스템 오류율

### Error Budget

정의한 SLO를 기준으로 허용 가능한 장애 시간과 오류량을 계산하고, 장애로 인해 Error Budget이 얼마나 소진되는지 확인한다.

### Runbook

장애 유형별로 다음 내용을 작성한다.

- 장애 증상
- 확인할 대시보드와 메트릭
- 로그 및 Trace 확인 방법
- Kubernetes 상태 확인 방법
- 임시 대응 방법
- 복구 확인 방법

## 10. 최종 프로젝트 설명

> 사용자가 지역과 날짜를 기준으로 호텔을 검색하고 객실 정보를 조회할 수 있는 웹 기반 호텔 예약 서비스를 제작한다. 특정 시간에는 한정된 수량의 호텔 특가 상품을 오픈하고, 이벤트 시작과 동시에 다수의 사용자가 접속하도록 부하를 발생시킨다.
>
> 사용자는 특가 호텔과 객실을 조회하고 예약을 요청하며, 시스템은 객실 재고 확인, 재고 차감 및 예약 생성을 처리한다. 추후에는 가상 대기열과 테스트용 결제 기능을 추가하여 트래픽 제어 및 장애 시나리오를 고도화한다.
>
> 프로젝트에서는 특가 예약 과정에서 발생하는 트래픽 증가, 응답 지연, 예약 실패, 객실 재고 경쟁, 시스템 과부하 및 장애 복구 상황을 메트릭·로그·분산 추적으로 분석한다.
>
> Prometheus, Grafana, Loki, Tempo 및 OpenTelemetry를 활용하여 Observability 환경을 구성하고, Alertmanager와 Slack을 통한 장애 알림, K6 기반 부하 테스트, 장애 시뮬레이션을 수행한다.
>
> 최종적으로 SLI·SLO와 Error Budget을 정의하고 장애 유형별 Runbook을 작성하여 장애 감지부터 원인 분석 및 복구까지 실제 운영과 유사한 대응 흐름을 검증한다.
