# 5. 프로젝트 과업 연계
<br>

## 5.1 시장·서비스 비교 분석
<br>

### 비교 대상

한정판매, 대규모 할인 행사, 가상 대기열, 순간 트래픽 급증이 발생하는 국내외 이커머스 서비스를 선정하여 비교합니다.

#### 국내 서비스 후보

- 쿠팡
- 무신사
- KREAM
<br>
#### 해외 서비스 후보

- Amazon
- Nike SNKRS
- Shopify 기반 대규모 판매 서비스

최종적으로 국내 서비스 2~3개와 해외 서비스 2~3개를 선정합니다.
<br>
### 비교 항목

- 추정 서비스 아키텍처
- CI/CD 및 배포 방식
- 대규모 트래픽 대응 방식
- 가상 대기열 적용 여부
- 재고 동시성 처리 방식
- 모니터링 및 장애 대응 방식
- MSA 적용 여부
- 서비스 메시 적용 여부
- 장애 및 운영 정보 공개 수준
<br>

### 운영 페인포인트

1. 한정판매 시작 순간 요청이 급증할 수 있습니다.
2. 재고 수량보다 많은 주문이 생성될 수 있습니다.
3. 대기열 처리 지연으로 사용자가 장시간 기다릴 수 있습니다.
4. 주문은 생성됐지만 결제가 실패할 수 있습니다.
5. 결제 실패 후 재고가 정상적으로 복구되지 않을 수 있습니다.
6. 여러 서비스 중 장애가 발생한 위치를 빠르게 찾기 어렵습니다.
7. 장애를 늦게 탐지하면 주문 실패와 사용자 이탈이 누적될 수 있습니다.
<br>

### 프로젝트 차별화 방향

- 대기열 진입부터 결제 완료까지 전체 구매 흐름을 관찰합니다.
- 사용자·주문·상품 단위로 로그를 검색할 수 있도록 구성합니다.
- 메트릭에서 이상을 감지한 후 관련 로그와 분산 추적으로 이동합니다.
- 대기열 길이와 평균 대기시간을 서비스 품질 지표로 사용합니다.
- 장애 알림과 Runbook을 연결하여 실제 복구 절차를 검증합니다.
- 한정판매 전·진행 중·종료 후의 성능 차이를 비교합니다.
<br>


## 5.2 환경 구축 및 Observability 아키텍처 설계
<br>

### 대상 서비스 배포

다음 3개의 백엔드 서비스를 오케스트레이터 환경에 배포합니다.

- `Commerce Service`
- `Queue Service`
- `Payment Service`

프론트엔드는 사용자가 다음 기능을 이용할 수 있는 화면을 제공합니다.

- 회원가입 및 로그인
- 일반 상품 조회
- 장바구니
- 한정판매 상품 확인
- 대기 순번 확인
- 상품 구매
- 결제 결과 확인
- 주문 내역 조회

### 서비스별 역할
<br>

#### Commerce Service

- 회원 관리
- 상품 조회
- 장바구니 관리
- 주문 생성
- 재고 처리
- 주문 상태 관리
<br>

#### Queue Service

- 한정판매 대기열 등록
- 대기 순번 조회
- 사용자 순차 입장
- 구매 권한 발급 및 만료
<br>

#### Payment Service

- 테스트 결제 처리
- 결제 성공·실패
- 결제 지연·시간 초과
- 결제 결과 전달
- 결제 실패 시 재고 복구 요청
<br>

### Observability 운영 흐름

```text
사용자 요청
→ Commerce·Queue·Payment Service 처리
→ 메트릭·로그·추적 정보 생성
→ 통합 대시보드에서 상태 확인
→ 이상 상태 알림 발생
→ 로그와 분산 추적으로 원인 분석
→ Runbook에 따라 복구
→ 정상화 여부 확인
```
<br>

### SLI·SLO 초안
<br>

#### 서비스 가용성

- **SLI:** 정상 처리된 유효 요청의 비율
- **SLO 예시:** 유효 요청의 99.9% 이상 정상 처리
<br>

#### 주문 응답시간

- **SLI:** 기준 시간 안에 완료된 주문 요청의 비율
- **SLO 예시:** 주문 요청의 95%가 500ms 이내 완료
<br>

#### 결제 성공률

- **SLI:** 정상 결제 시도 중 성공한 비율
- **SLO 예시:** 정상 결제 시도의 99% 이상 성공
<br>

#### 대기열 처리 성공률

- **SLI:** 대기열 등록·순번 조회·입장 처리가 정상 완료된 비율
- **SLO 예시:** 대기열 요청의 99.5% 이상 정상 처리
<br>

### 오류 측정 기준

다음과 같은 정상적인 비즈니스 거절은 시스템 장애와 구분합니다.

- 상품 품절
- 잘못된 비밀번호
- 중복 구매 요청
- 만료된 구매 권한
- 판매 시작 전 구매 요청
- 사용자 입력 오류

## 5.3 메트릭 수집 및 대시보드 구축

4 Golden Signals를 기준으로 4개의 대시보드를 구성합니다.

### 대시보드 1. 전체 서비스 현황

- 전체 요청 수
- 초당 요청 수
- 요청 성공률
- 오류율
- 평균 응답시간
- p95 응답시간
- p99 응답시간
- 서비스별 정상 상태
- 서비스별 요청 분포

### 대시보드 2. 대기열 현황

- 현재 대기자 수
- 초당 대기열 등록 수
- 초당 구매 화면 입장 사용자 수
- 평균 대기시간
- 최대 대기시간
- 구매 권한 발급 성공률
- 구매 권한 만료 수
- 대기열 등록 실패 수
- 대기열 이탈 사용자 수

### 대시보드 3. 주문·결제 현황

- 상품별 구매 시도 수
- 주문 생성 성공률
- 상품별 남은 재고
- 품절 응답 수
- 중복 구매 차단 수
- 결제 성공률
- 결제 실패율
- 결제 응답시간
- 결제 시간 초과 수
- 결제 실패 후 재고 복구 성공률

### 대시보드 4. 시스템 포화 상태

- 서비스 CPU 사용량
- 서비스 메모리 사용량
- 데이터 저장소 연결 사용량
- 처리 대기 요청 수
- 비동기 작업 적체량
- 서비스 재시작 수
- 대기열 길이
- 데이터 저장소 응답시간
- 인스턴스별 요청 처리량

### 4 Golden Signals 연계

| 신호 | 확인 항목 |
|---|---|
| Latency | 상품 조회·대기열·주문·결제 응답시간 |
| Traffic | 초당 요청 수·동시 사용자 수·구매 시도 수 |
| Errors | 서버 오류·주문 실패·결제 실패 |
| Saturation | CPU·메모리·연결 사용량·대기열 및 작업 적체 |

## 5.4 구조화 로그 및 쿼리 라이브러리

### 구조화 로그 필드

각 서비스의 로그에는 다음 정보를 포함합니다.

- 발생 시각
- 로그 수준
- 서비스명
- 사용자 식별값
- 상품 식별값
- 주문번호
- 요청 추적 번호
- 처리 상태
- 오류 코드
- 처리 시간
- 요청 경로
- 응답 상태 코드

### 로그 쿼리 후보

1. 최근 5분간 서버 오류 조회
2. 결제 실패 주문 조회
3. 특정 주문번호의 전체 처리 과정 조회
4. 특정 요청 추적 번호의 서비스별 로그 조회
5. 특정 사용자의 구매 흐름 조회
6. 특정 상품의 품절 처리 로그 조회
7. 중복 구매 차단 로그 조회
8. 결제 실패 후 재고 복구 실패 로그 조회
9. 구매 권한 만료 로그 조회
10. 서비스별 오류 발생 건수 조회

### 필요한 이유

단순히 오류 건수만 확인하는 것이 아니라 다음 내용을 정확히 분석하기 위해 사용합니다.

- 어떤 사용자에게 문제가 발생했는가
- 어떤 상품과 주문에서 오류가 발생했는가
- 어느 서비스에서 처음 오류가 발생했는가
- 결제 실패 후 재고가 복구되었는가
- 동일한 요청이 각 서비스에서 어떻게 처리되었는가

## 5.5 분산 추적 통합

### 일반 상품 구매 추적

```text
사용자 인증
→ 상품 조회
→ 장바구니 조회
→ 주문 생성
→ 결제
→ 주문 상태 변경
```

### 한정판매 상품 구매 추적

```text
사용자 인증
→ 대기열 입장 확인
→ 구매 권한 확인
→ 재고 차감
→ 주문 생성
→ 결제
→ 주문 상태 변경
→ 결제 실패 시 재고 복구
```

### 필요한 이유

분산 추적을 통해 다음 내용을 확인합니다.

- 전체 구매 요청의 End-to-End 처리 시간
- 각 서비스에서 소요된 시간
- 가장 오래 걸린 처리 구간
- 오류가 최초 발생한 서비스
- 데이터 저장소 호출 지연
- 결제 실패 이후 재고 복구 과정

### 메트릭·로그·추적 연계 흐름

```text
결제 응답시간 증가 메트릭 확인
→ 해당 시간대 결제 실패 로그 조회
→ 로그에서 요청 추적 번호 확인
→ 동일한 요청의 분산 추적 조회
→ 결제 처리 구간의 지연 또는 실패 원인 확인
```

## 5.6 알림 규칙 및 채널 통합

다음 알림 중 5~10개를 선정하여 구현합니다.

1. 전체 서버 오류율 증가
2. 주문 API p95 응답시간 초과
3. 결제 성공률 감소
4. 대기열 길이 임계값 초과
5. 평균 대기시간 임계값 초과
6. 구매 화면 입장 처리율 감소
7. 데이터 저장소 연결 사용률 증가
8. 비동기 작업 적체 증가
9. 서비스 재시작 발생
10. 서비스 가용성 SLO 위반

### 필요한 이유

운영자가 대시보드를 계속 확인하지 않아도 다음 상황을 빠르게 인지할 수 있도록 합니다.

- 사용자에게 영향을 주는 오류 발생
- 서비스 응답시간 저하
- 결제 실패 증가
- 대기열 처리 지연
- 시스템 자원 포화
- 서비스 인스턴스 장애
- SLO 위반 가능성

## 5.7 SLO 측정 및 Error Budget 계산

한정판매 전·진행 중·종료 후의 데이터를 구분하여 측정합니다.

### 측정 대상

- 서비스 가용성
- 주문 API p95 응답시간
- 결제 성공률
- 대기열 처리 성공률
- 서버 오류율
- 평균 대기시간
- 구매 성공률

### 보고서 포함 내용

- SLI 정의
- SLO 목표
- 측정 기간
- 실제 측정 결과
- 허용 가능한 실패량
- 실제 실패량
- Error Budget 총량
- Error Budget 잔여량
- 장애 발생 중 Error Budget 소모 속도
- Burn Rate
- 임계값 선정 근거

### 필요한 이유

서비스가 단순히 실행되는지만 확인하는 것이 아니라 다음을 판단하기 위해 필요합니다.

- 목표한 서비스 품질을 만족했는가
- 장애가 사용자에게 어느 정도 영향을 주었는가
- 허용 가능한 실패 범위를 얼마나 사용했는가
- 장애 대응과 개선 작업이 필요한 수준인가

## 5.8 부하 및 장애 시뮬레이션

### 부하 테스트 시나리오

한정판매 시작과 동시에 다수의 사용자가 다음 행동을 수행합니다.

```text
로그인
→ 한정상품 조회
→ 대기열 등록
→ 대기 순번 반복 조회
→ 구매 화면 입장
→ 주문 생성
→ 결제
→ 주문 결과 조회
```

### 장애 시나리오 1. 결제 지연

#### 수행 내용

- 결제 처리 시간을 의도적으로 증가시킵니다.

#### 확인 항목

- 결제 응답시간
- 전체 구매 완료 시간
- p95·p99 응답시간
- 처리 대기 요청 수
- 분산 추적에서 결제 구간의 지연 시간
- 관련 알림 발생 여부

---

### 장애 시나리오 2. 결제 실패

#### 수행 내용

- 일정 비율의 결제 요청을 실패 처리합니다.

#### 확인 항목

- 결제 실패율
- 전체 오류율
- 결제 성공률 알림
- 실패 주문 로그
- 결제 실패 Trace
- 주문 상태 변경
- 재고 복구 성공 여부

---

### 장애 시나리오 3. Queue Service 강제 종료

#### 수행 내용

- 대기열 서비스 인스턴스를 강제로 종료합니다.

#### 확인 항목

- 대기열 등록 성공률
- 대기 순번 조회 성공률
- 사용자 오류 발생 여부
- 서비스 자동 복구 시간
- 재시작 횟수
- 복구 후 정상 처리 여부

---

### 장애 시나리오 4. Commerce Service CPU 부하

#### 수행 내용

- 상품·주문 서비스에 CPU 부하를 발생시킵니다.

#### 확인 항목

- CPU 사용량
- 상품 조회 응답시간
- 주문 API p95 응답시간
- 오류율
- 처리 대기 요청 수
- 자원 포화 알림 발생 여부

---

### 장애 시나리오 5. 데이터 저장소 연결 부족

## 5.9 Runbook 작성

알림 및 장애 시나리오에 대응하는 Runbook을 5~10개 작성합니다.

### Runbook 후보

1. 서버 오류율 증가
2. 주문 API p95 응답시간 증가
3. 결제 성공률 감소
4. 대기열 길이 급증
5. 평균 대기시간 증가
6. 데이터 저장소 연결 부족
7. 비동기 작업 적체
8. 서비스 재시작
9. 재고 복구 실패
10. 서비스 가용성 SLO 위반

### Runbook 예시: 결제 성공률 감소

```text
결제 성공률 감소 알림 수신
→ 결제 서비스 상태 확인
→ 최근 결제 오류 로그 조회
→ 실패 주문의 요청 추적 번호 확인
→ 분산 추적으로 실패 구간 확인
→ 결제 지연·서비스 장애·데이터 저장소 오류 여부 확인
→ 장애 원인 제거
→ 실패 주문 상태 확인
→ 재고 복구 상태 확인
→ 결제 성공률 정상화 확인
→ 장애 발생 시간과 영향 범위 기록
```

### 필요한 이유

장애 발생 시 담당자가 임의로 대응하는 것이 아니라, 정해진 절차에 따라 빠르고 일관되게 대응할 수 있도록 합니다.

## 5.10 통합 케이스 스터디 및 라이브 데모

### 통합 케이스 스터디 흐름

```text
이커머스 운영 페인포인트 분석
→ 한정판매 서비스 설계
→ Observability 아키텍처 설계
→ 대상 서비스 배포
→ 메트릭·로그·분산 추적 통합
→ SLI·SLO 정의
→ 부하 및 장애 주입
→ 장애 알림 발생
→ 로그와 분산 추적으로 원인 분석
→ Runbook 기반 복구
→ 정상화 확인
→ Error Budget 및 Burn Rate 영향 분석
```

### 라이브 데모 흐름

1. 정상 상태의 서비스와 대시보드를 확인합니다.
2. 한정상품 판매 시작 시간을 확인합니다.
3. 다수의 사용자를 대기열에 진입시킵니다.
4. RPS·대기열 길이·응답시간 증가를 확인합니다.
5. 사용자들이 순차적으로 구매 화면에 입장하는 것을 확인합니다.
6. 결제 서비스에 지연 또는 실패를 발생시킵니다.
7. 오류율과 p95 응답시간 증가를 확인합니다.
8. 장애 알림이 전달되는 것을 확인합니다.
9. 실패 요청의 구조화 로그를 조회합니다.
10. 로그에서 요청 추적 번호를 확인합니다.
11. 분산 추적으로 결제 장애 구간을 확인합니다.
12. Runbook에 따라 장애 원인을 제거합니다.
13. 서비스 정상화와 복구 시간을 확인합니다.
14. 결제 실패 주문과 재고 복구 상태를 확인합니다.
15. 장애가 SLO와 Error Budget에 미친 영향을 설명합니다.
