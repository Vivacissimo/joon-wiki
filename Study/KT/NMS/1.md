# NoMoreSh Dev 환경 배포 트러블슈팅 정리

## 1. 최종 결과

현재 Dev 환경의 GitOps 배포 흐름은 정상 동작합니다.

```text
코드 수정
→ GitHub Push
→ GitHub Actions 실행
→ 변경 서비스 이미지 빌드
→ GHCR 이미지 Push
→ values-dev.yaml 이미지 태그 자동 변경
→ Git Commit
→ ArgoCD Auto Sync
→ Kubernetes Rolling Update
→ 모든 리소스 Synced / Healthy
```

최종 확인 상태:

- GitHub Actions 성공
- GHCR 이미지 Push 성공
- ArgoCD `Synced`
- ArgoCD `Healthy`
- 모든 애플리케이션 Pod `2/2 Running`
- Spring 서비스와 PostgreSQL 연결 정상
- Eureka Server 정상
- API Gateway 정상
- NetworkPolicy 적용 상태에서 Namespace 내부 통신 정상
- Startup Probe 적용으로 느린 Spring Boot 기동 대응 완료

# 2. 최초 증상

GitHub Actions 배포는 성공했지만 ArgoCD에서 다음 상태가 표시됐습니다.

```text
SYNC STATUS: Synced
LAST SYNC: Sync OK
APP HEALTH: Progressing
```

의미:

- Git에 있는 Kubernetes 설정은 정상 반영됨
- ArgoCD Sync 자체는 성공
- 하지만 실제 Pod가 Ready 상태가 되지 못함
- 따라서 배포 작업은 끝났지만 애플리케이션 상태는 비정상

Pod 조회 결과 다수의 서비스가 다음 상태였습니다.

```text
1/2 Running
CrashLoopBackOff
Readiness Probe 실패
Liveness Probe 실패
```

DB Pod는 정상인데 Patient, Appointment, Notification, Prescription 서비스가 모두 반복 재시작되고 있었습니다. :contentReference[oaicite:0]{index=0}


# 4. 트러블슈팅 2 — Spring 서비스의 PostgreSQL 연결 실패

## 증상

각 서비스의 이전 컨테이너 로그를 확인했습니다.

```bash
kubectl logs -n dev \
  <POD_NAME> \
  -c <CONTAINER_NAME> \
  --previous \
  --tail=200
```

Patient, Appointment, Notification, Prescription 서비스에서 동일한 오류가 발생했습니다.

```text
org.postgresql.util.PSQLException: The connection attempt failed
java.net.SocketTimeoutException: Read timed out
Unable to open JDBC Connection
Failed to initialize JPA EntityManagerFactory
```

Spring Boot가 PostgreSQL에 연결하지 못해 JPA 초기화에 실패했고, ApplicationContext가 종료됐습니다. :contentReference[oaicite:1]{index=1}

## 판단

비밀번호 오류였다면 일반적으로 다음 메시지가 나와야 합니다.

```text
password authentication failed
```

하지만 실제 오류는 다음과 같았습니다.

```text
SocketTimeoutException
Read timed out
```

따라서 인증 이전 단계에서 네트워크 패킷이 차단되고 있다고 판단했습니다.

# 7. 트러블슈팅 5 — NetworkPolicy가 DB 통신 차단

## 기존 NetworkPolicy

```bash
kubectl get networkpolicy -n dev
kubectl get networkpolicy -n dev -o yaml
```

기존 정책:

```text
default-deny-all
allow-traffic-from-istio-gateway
allow-traffic-generator-to-envoy-test
```

`default-deny-all` 설정:

```yaml
spec:
  podSelector: {}
  policyTypes:
    - Ingress
```

이 정책은 `dev` Namespace의 모든 Pod에 대해 Ingress를 기본 차단합니다.

허용된 트래픽은 다음뿐이었습니다.

```text
istio-ingressgateway → dev Pod
traffic-generator → envoy-test:80
```

하지만 서비스와 DB 간 통신을 허용하는 정책이 없었습니다.

```text
patient-service → patient-db:5432       차단
appointment-service → appointment-db    차단
notification-service → notification-db  차단
prescription-service → prescription-db  차단
```

## 원인

DB Pod 내부의 `127.0.0.1:5432` 통신은 NetworkPolicy 적용 대상이 아니므로 성공했습니다.

반면 다른 Pod에서 DB Pod로 들어오는 TCP 5432 요청은 `default-deny-all`에 의해 차단됐습니다.

```text
Spring Service Pod
→ ClusterIP Service
→ PostgreSQL Pod
→ NetworkPolicy에서 Drop
→ JDBC Read Timeout
→ JPA 초기화 실패
→ Spring Boot 종료
→ CrashLoopBackOff
```

# 8. NetworkPolicy 수정

## 생성한 정책

`charts/medical/templates/networkpolicy.yaml`

```yaml
{{- if .Values.networkPolicy.allowSameNamespace }}
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-same-namespace
spec:
  podSelector: {}
  policyTypes:
    - Ingress
  ingress:
    - from:
        - podSelector: {}
{{- end }}
```

## 기본 values 설정

`charts/medical/values.yaml`

```yaml
networkPolicy:
  allowSameNamespace: false
```

기본 환경에서는 비활성화해 의도하지 않은 적용을 방지했습니다.

## Dev 환경 설정

`charts/medical/values-dev.yaml`

```yaml
networkPolicy:
  allowSameNamespace: true
```

Dev 환경에서만 활성화했습니다.

## 정책 적용 후 통신 범위

```text
dev Namespace Pod → dev Namespace Pod       허용
다른 Namespace Pod → dev Namespace Pod      기본 차단
Istio Gateway → dev Namespace Pod           기존 정책으로 허용
```

`default-deny-all`은 삭제하지 않았습니다.

NetworkPolicy는 Deny 규칙을 덮어쓰는 방식이 아니라, 허용 규칙들이 합쳐지는 방식으로 적용됩니다.

# 10. 트러블슈팅 6 — Eureka Server 반복 재시작

## 증상

Eureka Server 로그에서는 애플리케이션 오류가 없었습니다.

```text
Started EurekaApplication in 98.092 seconds
```

정상 기동 직후 다음 로그가 발생했습니다.

```text
Unregistering application UNKNOWN
Shutting down Eureka Server
```

## 원인

Eureka Server가 정상 기동하는 데 약 94~98초가 걸렸습니다.

하지만 기존 Liveness Probe가 애플리케이션 기동 완료 전에 실패 횟수를 초과해 컨테이너를 종료시키고 있었습니다.

```text
Spring Boot 기동 중
→ Liveness Probe 실패
→ failureThreshold 초과
→ kubelet이 SIGTERM 전송
→ Eureka 종료
→ 재시작
```

## 해결

`startupProbe`를 추가해 애플리케이션 기동 중에는 Liveness Probe가 동작하지 않도록 했습니다.

```yaml
startupProbe:
  httpGet:
    path: {{ dig "probe" "startupPath" "/health" $svc }}
    port: {{ $svc.port }}
  periodSeconds: 10
  timeoutSeconds: 3
  failureThreshold: 18
```

최대 기동 대기 시간:

```text
10초 × 18회 = 180초
```

Eureka가 약 100초 정도 걸려 기동해도 Kubernetes가 강제 재시작하지 않게 됐습니다.

최종 결과:

```text
eureka-server   2/2 Running   RESTARTS 0
```

# 11. 트러블슈팅 7 — Dashboard Startup Probe 경로

Dashboard는 Nginx 기반이며 기본 페이지가 `/` 경로에 있습니다.

하지만 공통 Startup Probe 기본 경로는 `/health`였습니다.

```yaml
path: {{ dig "probe" "startupPath" "/health" $svc }}
```

Dashboard에 `startupPath`가 없으면 `/health` 요청이 404가 될 수 있었습니다.

## 수정

`values.yaml`

```yaml
dashboard:
  probe:
    type: http
    startupPath: /
    readinessPath: /
    livenessPath: /
```

결과:

```text
dashboard   2/2 Running
```

# 13. API Gateway Degraded 원인 분석

## Pod Describe 결과

```bash
kubectl describe pod api-gateway-5fb898d468-m9lsd -n dev
```

Events:

```text
Startup probe failed: HTTP probe failed with statuscode: 500
Startup probe failed: HTTP probe failed with statuscode: 404
Container api-gateway failed startup probe, will be restarted
```

컨테이너 상태:

```text
Last State: Terminated
Reason: Error
Exit Code: 143
```

`Exit Code 143`:

```text
128 + SIGTERM(15) = 143
```

즉, 애플리케이션 자체 오류가 아니라 Kubernetes가 Probe 실패로 SIGTERM을 보내 종료한 것입니다.

## 애플리케이션 로그

API Gateway는 정상적으로 기동하고 있었습니다.

```text
Eureka response status is 200
registration status: 204
Netty started on port 8080
Started GatewayApplication
```

정상 기동 이후 Shutdown Hook이 실행됐습니다.

```text
Unregistering application API-GATEWAY
Shutting down DiscoveryClient
```

따라서 원인은 애플리케이션이 아니라 Probe 설정이었습니다. :contentReference[oaicite:4]{index=4}

# 14. API Gateway Startup Probe 설정 오류

API Gateway는 기존 설정에서 TCP Probe를 사용하고 있었습니다.

```yaml
probe:
  type: tcp
```

Readiness와 Liveness는 TCP 방식이었지만 새로 추가한 Startup Probe는 모든 서비스에 HTTP `/health`를 강제 적용했습니다.

문제가 된 구조:

```yaml
startupProbe:
  httpGet:
    path: /health
    port: 8080
```

API Gateway의 `/health`가 Startup Probe 기준으로 404 또는 초기화 중 500을 반환하면서 컨테이너가 반복 재시작됐습니다.

---

# 15. Startup Probe 템플릿 수정

`deployment.yaml`에서 `probe.type`에 따라 Startup Probe 방식도 나누도록 수정했습니다.

```yaml
startupProbe:
  {{- if eq (dig "probe" "type" "http" $svc) "tcp" }}
  tcpSocket:
    port: {{ $svc.port }}
  {{- else }}
  httpGet:
    path: {{ dig "probe" "startupPath" "/health" $svc }}
    port: {{ $svc.port }}
  {{- end }}
  periodSeconds: 10
  timeoutSeconds: 3
  failureThreshold: 18
```

최종 동작:

| 서비스 | Probe 타입 | Startup Probe |
|---|---|---|
| API Gateway | TCP | TCP 8080 |
| Eureka Server | TCP | TCP 8761 |
| Patient Service | HTTP | `/health` |
| Appointment Service | HTTP | `/health` |
| Prescription Service | HTTP | `/health` |
| Notification Service | HTTP | `/health` |
| Dashboard | HTTP | `/` |

## 결과

새 API Gateway Pod가 정상화됐고 Rolling Update가 완료됐습니다.

```text
새 ReplicaSet Pod 2/2 Running
기존 ReplicaSet Replica 0
ArgoCD Degraded 해제
ArgoCD Healthy
```

# 17. 트러블슈팅 10 — kubectl이 잘못된 EKS Context를 참조

## 증상

로컬에서 Dry Run 실행 중 다음 오류가 발생했습니다.

```text
failed to download openapi
dial tcp: lookup <EKS-ENDPOINT>: no such host
```

## 원인

로컬 `kubectl`의 현재 Context가 외부 Dev 클러스터가 아니라 AWS EKS를 가리키고 있었습니다.

`--dry-run=client`여도 Kubernetes OpenAPI Schema 검증을 위해 현재 Context의 API Server에 접근할 수 있습니다.

## 확인

```powershell
kubectl config current-context
kubectl config get-contexts
```

## 임시 해결

클러스터 연결 없이 렌더링 결과를 검사할 때:

```powershell
helm template medical charts/medical -n dev -f charts/medical/values-dev.yaml |
  kubectl apply --dry-run=client --validate=false -f -
```

Helm 자체 검사:

```powershell
helm lint charts/medical -f charts/medical/values-dev.yaml
```

실제 Dev 클러스터 검증은 Master 서버에서 수행하는 것이 가장 정확합니다.

```bash
helm template medical charts/medical \
  -n dev \
  -f charts/medical/values-dev.yaml \
  | kubectl apply --dry-run=server -f -
```

# 18. Rolling Update 중 Pod가 여러 개 보였던 이유

서비스마다 서로 다른 ReplicaSet 해시의 Pod가 동시에 존재했습니다.

```text
patient-service-56f8567854-...
patient-service-5ccf658dc4-...
patient-service-7fd675dbbd-...
```

이는 중복 배포가 아니라 Rolling Update가 중간에 멈춘 상태였습니다.

```text
기존 ReplicaSet Pod 정상
→ 새 ReplicaSet 생성
→ 새 Pod Probe 실패
→ 새 Pod Ready 실패
→ 기존 Pod를 제거하지 못함
→ 여러 ReplicaSet Pod가 동시에 존재
```

새 Pod가 정상화된 후 Kubernetes가 자동으로 기존 ReplicaSet의 Replica를 0으로 줄였습니다.

기존 ReplicaSet 객체는 롤백 기록을 위해 남아 있을 수 있습니다.

```text
ReplicaSet이 남아 있음       정상
Replica가 0보다 큼           배포 진행 중 또는 문제 가능
```

# 20. 핵심 원인과 해결 요약

| 문제 | 직접 원인 | 해결 |
|---|---|---|
| ArgoCD `Progressing` | Pod가 Ready 상태가 되지 않음 | Pod, Events, Logs 확인 |
| 4개 Spring 서비스 CrashLoopBackOff | PostgreSQL 연결 타임아웃 | NetworkPolicy 수정 |
| DB 접속 실패 | `default-deny-all`이 DB Pod Ingress 차단 | `allow-same-namespace` 추가 |
| Eureka 반복 재시작 | 기동 완료 전 Liveness Probe 실패 | Startup Probe 추가 |
| Dashboard Probe 위험 | `/health` 경로 없음 | `startupPath: /` 설정 |
| API Gateway Degraded | TCP 서비스에 HTTP Startup Probe 사용 | `probe.type`별 Startup Probe 분기 |
| API Gateway Exit 143 | kubelet이 Probe 실패로 SIGTERM 전송 | 올바른 TCP Startup Probe 적용 |
| PowerShell ParserError | Bash의 `\` 사용 | PowerShell 백틱 또는 한 줄 실행 |
| OpenAPI 조회 실패 | kubectl이 연결 불가능한 EKS Context 참조 | `--validate=false` 또는 올바른 Context 사용 |
| 여러 ReplicaSet Pod 존재 | 새 Pod Ready 실패로 Rolling Update 중단 | 새 Pod 문제 해결 후 자동 정리 |
